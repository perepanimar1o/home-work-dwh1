# ДЗ №1. Источники данных и отказоустойчивый кластер — «Аптека 108»

Четыре независимых источника (CRM, каталог, POS, склад) для сети аптек: каждый — **отдельная база PostgreSQL 18** со своей моделью, инвариантами, схемой `contract` для будущего DWH,
репликацией и подготовкой к CDC; все четыре живут в **кластере Patroni** (3 узла + etcd из 3 узлов + HAProxy + PgBouncer). Условие задания — [`docs/assignment/ASSIGNMENT.md`](docs/assignment/ASSIGNMENT.md).

> Состояние самопроверки: `python hw01_check.py --submission ./hw01_submission.yaml` на стенде, собранном **с нуля** (`docker compose down -v` → `up` → `seed`), — **все автоматические проверки зелёные: 21 из 21** возможных автоматически баллов
> (контракт 4, данные и целостность 4, реплика и пул 2, инварианты 5, HA 2, CDC 1, реалистичность 1, одиночное выполнение 2). Вручную проверяются: карта склейки, журнал решений (ADR), журнал отказоустойчивости, кворумный etcd.

## Быстрый старт

Нужны Docker (Compose v2) и Python 3.9+. Образы скачиваются и собираются при первом запуске (несколько минут, нужен интернет; повторные запуски — секунды).

```bash
pip install -r requirements.txt                 # psycopg2-binary, PyYAML — для чекера (и для генератора; без них генератор сам запустится в контейнере)

docker compose up -d --build                    # 9 контейнеров: 3 etcd, 3 PostgreSQL (Patroni), HAProxy, 2 PgBouncer
./scripts/wait_ready.sh                         # возвращается, когда кластер собран и все 4 БД созданы миграциями (≈ 20 с)
./scripts/seed.sh --seed 42                     # данные: 24 тыс. чеков, 65 тыс. позиций, 91 тыс. движений (≈ 8 с)
python hw01_check.py --submission ./hw01_submission.yaml   # самопроверка тем же чекером, что у преподавателя
```

Остановка и полная очистка (удаляет тома с данными — **обязательно** после правки миграций: скрипты инициализации выполняются только на пустом PGDATA):

```bash
docker compose down -v
```

Генератор: `./scripts/seed.sh --seed 42` идемпотентен (повторный запуск ничего не меняет); `./scripts/seed.sh --seed 777 --receipts 500` **догенерирует** 500 чеков поверх существующих данных
(с продажами из реальных остатков аптек и соответствующими движениями склада; при каждом запуске добавляет новые чеки).

### Строки подключения

На macOS порты 5000 и 7000 занимает AirPlay Receiver, поэтому HAProxy опубликован на **5400/5401**.

| назначение | порт | строка подключения (пример для `pos_service_db`) |
|------------|------|--------------------------------------------------|
| **PgBouncer → лидер** (запись + чтение), основной вход приложения | 6432 | `postgresql://app:app@localhost:6432/pos_service_db` |
| **PgBouncer → реплики** (только чтение) | 6433 | `postgresql://checker:checker@localhost:6433/pos_service_db` |
| **HAProxy → лидер** (мимо пула; CDC, генератор, администрирование) | 5400 | `postgresql://postgres:postgres@localhost:5400/pos_service_db` |
| **HAProxy → реплики** | 5401 | `postgresql://postgres:postgres@localhost:5401/pos_service_db` |
| Patroni REST API (`pg1`/`pg2`/`pg3`) | 8008 / 8009 / 8010 | `http://localhost:8008/cluster` |
| статистика HAProxy | 7070 | `http://localhost:7070/` |

Базы: `crm_service_db`, `catalog_service_db`, `pos_service_db`, `wms_service_db`. Роли: `app` (владелец объектов; приложение и негативные тесты), `checker` (`SELECT` на схему `contract` + `pg_monitor`), `postgres` (суперпользователь).
Пароли учебные (`app`/`checker`/`postgres`), `pg_hba` пускает из любой сети docker — для стенда, не для боевой системы.

## Как устроена модель

**Сервисы и данные.** `crm` — клиенты, контакты, версионируемые согласия, карты лояльности; `catalog` — SKU, МНН (многие-ко-многим), производители, формы, цены с историей; `pos` — аптеки, кассы, смены, кассовые документы (продажи и возвраты), позиции, оплаты, рецепты;
`wms` — поставщики, РЦ, закупки, партии, журнал движений, остатки. Подробные схемы — в [`docs/erd/`](docs/erd/).

**Жёсткие требования задания:**

| требование | как выполнено |
|------------|---------------|
| business key, а не `serial` | текстовые BK с `CHECK` формата и триггером неизменяемости: `SKU-000148`, `PH-0342`, `BATCH-2026-04417`, `RCPT-20261014-000731`…; суррогаты (`identity`) — только внутри базы ([ADR-0001](docs/adr/0001-business-key-format.md)) |
| нет FK между БД | четыре разные базы в одном кластере — кросс-БД ссылка в PostgreSQL физически невозможна ([ADR-0006](docs/adr/0006-four-databases-one-cluster.md)); ссылки по BK, логические ссылки перечислены в [`docs/erd/`](docs/erd/) |
| технические поля | `created_at`, `updated_at` (обновляется триггером, не приложением), `source_system` |
| история там, где атрибут меняется | цены — SCD2 ([ADR-0002](docs/adr/0002-price-history-scd2.md)); название/категория/Rx SKU, город/уровень клиента, адрес аптеки — таблицы `*_history` ([ADR-0005](docs/adr/0005-attribute-history-via-trigger.md)) |
| snapshot-поля | в позиции чека: `unit_price`, `sku_name_snapshot`, `is_rx_snapshot` |
| soft delete | `deleted_at`/`is_active` в справочниках; физический `DELETE` запрещён триггером; клиент при удалении обезличивается (ПДн обнуляются, согласия отзываются, карты закрываются) |
| деньги | `numeric(…, 2)`, валюта — `char(3)` (ISO 4217, `CHECK upper`) |

### Контракт

Во всех четырёх базах — схема `contract` с 14 представлениями ровно по `hw01_contract.yaml`. Представления **детерминированы**: нет `now()`, `current_date`, `random()` — отпечатки мастера и реплики совпадают
(`is_current` у цены — хранимый флаг, а не вычисление через `now()`). Содержимое контракта воспроизводимо: две независимые загрузки с нуля дают одинаковые отпечатки всех 14 представлений
(исключение — `v_stock.updated_at`: у остатков это часы БД, ADR-0003).

### Отказоустойчивость

Patroni (3 узла, `ttl/loop_wait/retry_timeout = 30/10/10 с`) + etcd (кворум 2 из 3) + HAProxy (`:5400` лидер, `:5401` реплики по проверкам `/primary` и `/replica`) + PgBouncer (`transaction`, `:6432`/`:6433`). Асинхронная потоковая репликация со слотами;
синхронный режим включается `patronictl edit-config -s synchronous_mode=true` и измерен в журнале. **Журнал отказоустойчивости** — [`docs/failover_journal.md`](docs/failover_journal.md): эксперименты Э1–Э8 по шаблону + два дополнительных (`DROP TABLE`, холодный старт),
у каждого команда, сырой вывод/лог с таймстемпами, измеренное число и вывод. Главное из измерений: RTO аварии лидера 25–33 с (плановое переключение — 4.7 с), асинхронная репликация потеряла 2 748 подтверждённых транзакций там, где синхронная — 0 (цена: −16 % TPS), падение двух из трёх etcd переводит кластер в read-only за 11 с.

**Осознанная оговорка про версию Patroni** ([ADR-0007](docs/adr/0007-patroni-version.md)): закреплён Patroni **3.0.0**, потому что чекер ждёт у всех узлов `state == "running"`, а все проверенные Patroni ≥ 3.0.4 отдают у реплик `streaming`
(на 4.1.5 раздел HA давал `running 1 из 3`). Это особенность проверки, а не неисправность кластера; версию можно поднять одним build-аргументом `PATRONI_VERSION`, как только проверку исправят.

### CDC-готовность (задел для ДЗ №2)

`wal_level = logical` (динамическая конфигурация Patroni), `CREATE PUBLICATION hw01_cdc FOR ALL TABLES` в каждой базе (новые таблицы подхватываются автоматически), у всех таблиц есть `PRIMARY KEY` (`REPLICA IDENTITY DEFAULT` пригоден), поле инкремента `updated_at`, удаления — soft delete.
CDC-инструмент должен подключаться к лидеру **напрямую** (`:5400`), а не через PgBouncer. Подробности — в [`docs/dwh_mapping.md`](docs/dwh_mapping.md), §6.

## Допущения (зафиксированы по заданию)

1. Четыре базы живут в одном кластере PostgreSQL (учебное упрощение); для боевой системы с разными вендорами — четыре кластера (ADR-0006).
2. Валюта везде `RUB`. Бизнес-логика работает по московскому времени (смены 08:00–22:00 МСК, BK чека содержит локальную дату), хранение — `timestamptz` в UTC.
3. Один кассовый документ — либо продажа, либо возврат; возврат по продаже может быть частичным и несколько раз (в сумме не более проданного). Возвращённый лекарственный товар **не** возвращается в остаток (правила фармрозницы).
4. Приоритет цен «аптека > регион > сеть» применяет потребитель, а не БД; `scope_bk` региона — название региона как в `pos.pharmacy.region`.
5. Продажа списывает остаток аптеки движением `sale_writeoff`, **агрегированным за неделю** на пару (аптека, партия) — иначе было бы ≈ 65 тыс. движений только на продажи. Склад аптеки пополняется перемещением из РЦ **по потребности** (при нехватке в момент продажи).
6. Списание просрочки и редкий брак — движения `writeoff`; около 130 возвратов близких к сроку партий поставщику — `return`.
7. Номера BK выдаёт сервис-владелец (в сиде — счётчики генератора); в боевой системе нужен аллокатор (ADR-0001).
8. Локальные справочники `pos.sku_ref` и `pos.batch_ref` наполняются из «событий» каталога и склада; в сиде это делает генератор в той же загрузке (ADR-0004).
9. Синтетические данные: у закупок (69.8 млн ₽) стоимость выше выручки (48.2 млн ₽) — склад накапливает запас из-за начальной закупки и минимальных лотов; цены закупки 55–75 % розничной. Для задач ДЗ №3 это нужно учитывать.

## Генератор данных и «реалистичность» (бонус)

Единый «мир» на четыре БД: закупки → приёмка на РЦ → перемещения в аптеки → продажи; триггер склада проверяет остатки на каждом шаге, поэтому данные не могут быть «потенциально отрицательными».
Объёмы (минимум в скобках): клиентов 2 500 (2 000), карт 1 950 (1 500), SKU 650 (500), версий цен 3 077 (1 500), аптек 40 (30), РЦ 4 (3), поставщиков 12 (10), партий 13 734 (3 000), чеков 24 244 (20 000), позиций 65 016 (60 000), оплат 26 963 (20 000), строк закупок 13 885 (5 000), движений 91 084 (20 000), остатков 35 317 (5 000).
Распределения: недельная сезонность (`Пн 1.00, Вт 0.95, Ср 0.95, Чт 1.00, Пт 1.15, Сб 1.45, Вс 0.70`; max/min по дням недели ≈ 2.2) с годовой синусоидой и трендом; популярность SKU по Zipf (`s = 0.9`; топ-10 % SKU — ≈ 65 % выручки);
неравномерность аптек — lognormal (σ = 0.5; коэффициент вариации ≈ 0.54); покупки без карты — 43 %; возвраты — 3.3 % документов; интенсивность клиентов — степенное распределение (`1/ранг^0.7`).
Детерминизм: `random.Random` с составным seed (`{seed}:reference`, `:world`, `:docs`) — одинаковый `--seed` даёт одинаковые данные.

## Известные ограничения (честно)

- В манифесте `hw01_submission.yaml` ФИО, GitHub-логины и признак `solo` — **заглушки**: заполнить перед сдачей (при `solo: true` чекер начисляет +2 балла за одиночное выполнение, при сдаче командой поставьте `false`).
- Логические ссылки между сервисами не защищены СУБД (по условию); целостность держит генератор и проверяют кросс-проверки чекера. Удаление клиента не обезличивает `customer_bk` в чеках POS (см. `docs/dwh_mapping.md` §7).
- Нет бэкапов и PITR (реплики и failover не защищают от логической ошибки — журнал Э9), нет второго ЦОД; на стенде всё живёт на одном хосте.
- Watchdog для Patroni не настроен; пароли и `pg_hba` — учебные.
- RTO, TPS и прочие числа журнала измерены на одном стенде (Apple M4 Pro, Docker Desktop) — на другом железе значения будут другими (механизмы и порядок величин сохранятся).
