# ADR-0001. Формат business key

## Контекст
Хранилище (ДЗ №2) строится на business key (BK): хабы и линки ссылаются на BK, а не на внутренние суррогаты. Источники будут перезаливаться (в этом ДЗ — `seed.sh`, в жизни — восстановление из дампа),
поэтому BK обязан быть **стабильным, естественным, человекочитаемым, неизменным**. Условие задания прямо запрещает `serial` в роли BK. BK нужен на каждой сущности, которая пересекает границу сервиса
(клиент, SKU, аптека, партия, чек, поставщик, РЦ, закупка), потому что кросс-сервисных FOREIGN KEY нет и ссылки между сервисами — только по BK.

## Рассмотренные варианты
1. **`serial`/`identity` как внешний ключ** — запрещён условием; к тому же значение зависит от порядка вставки: перезаливка в другом порядке даёт другие id для тех же клиентов, и все ссылки из других систем «едут».
2. **UUID v4** — стабилен при перезаливке, если хранить его, но **не человекочитаем** (требование README), неудобен для сверки с бумажными документами и логами, плохая локальность B-tree-индекса (случайные вставки).
3. **Составной естественный ключ** (например, чек = аптека + смена + номер документа) — самый «настоящий», но многоколоночный BK усложняет хабы DWH и кросс-сервисные ссылки (в каждую таблицу-ссылку пришлось бы тащить три колонки).
4. **Префикс + zero-padded номер с проверкой формата** — `SKU-000148`, `PH-0342`, `BATCH-2026-04417`, `RCPT-20261014-000731`, `CUST-000001`.

## Выбор
Вариант 4. Формат закреплён `CHECK (… ~ '^SKU-[0-9]{6}$')` на каждой таблице, уникальность — `UNIQUE`, неизменность — триггером `util.forbid_bk_update` (инвариант I2).
Суррогатные ключи (`bigint GENERATED ALWAYS AS IDENTITY`) остаются **внутри** базы для FK; наружу (в `contract` и в другие сервисы) отдаётся только BK.
У чека и партии в BK зашита дата (`RCPT-ГГГГММДД-…`, `BATCH-ГГГГ-…`) — по BK видно, когда документ создан, и номер удобно сбрасывать по периодам.

## Отвергнутая альтернатива и причина
**UUID** отвергнут: он не удовлетворяет требованию человекочитаемости (оператор не продиктует UUID по телефону, аудитор не найдёт чек по бумажному номеру), а выигрыш — независимое от координатора создание ключа — нам не нужен:
BK выдаёт сам сервис-владелец. **`serial` отвергнут** безусловно (условие задания и поведение при перезаливке).

## Цена выбора
- Нужен **аллокатор номеров**: в продакшене — отдельная последовательность на каждый префикс/период (иначе гонка за «следующим номером»). В генераторе это счётчики по дням (`seed.py`: `numbers[date]`).
- **Ёмкость номера ограничена шириной**: `BATCH-ГГГГ-NNNNN` вмещает 99 999 партий в год. Сид даёт ≈ 13.7 тыс., но у сети с 12 тыс. SKU и 600 аптек этого может не хватить — тогда ширину нужно расширять
  (миграция `CHECK` + пересоздание индекса), а потребители BK не должны парсить его как число.
- Дата в BK = BK нельзя «переместить» на другой день (корректировка даты чека — это новый документ, а не `UPDATE`).
