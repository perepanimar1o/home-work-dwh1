# ADR-0006. Топология: четыре базы в одном кластере Patroni

## Контекст
Условие: четыре сервиса — это четыре **разные базы данных** (не схемы), но допускается один хост PostgreSQL. Нужны репликация, HA (Patroni + etcd + HAProxy), PgBouncer и подготовка к CDC. Ресурсы стенда ограничены (Docker VM: 12 vCPU, 8 ГБ RAM).

## Рассмотренные варианты
1. **Одна база, четыре схемы** — запрещено условием; к тому же схемы одной базы **допускают** кросс-схемные FOREIGN KEY, то есть можно случайно нарушить требование «никаких FK между сервисами».
2. **Четыре независимых кластера** (4 × 3 узла PostgreSQL + отдельные etcd/HAProxy) — самая «чистая» изоляция.
3. **Один кластер Patroni (3 узла) с четырьмя базами** — создаются в `post_bootstrap`, реплицируются вместе.

## Выбор
Вариант 3. В PostgreSQL запрос и ссылка между базами одного кластера невозможны (нет кросс-БД JOIN/FK), так что требование «никаких FK между базами» обеспечивается **самой СУБД**, а не дисциплиной.
Роли: `app` — владелец объектов (под ней приложение и негативные тесты), `checker` — только `SELECT` на `contract` + `pg_monitor` (чтение статистики репликации), `postgres` — администрирование и publication.

## Отвергнутая альтернатива и причина
**Четыре кластера (вариант 2)** отвергнут из-за ресурсов и операционной сложности: 12 узлов PostgreSQL + по три узла etcd на 8 ГБ памяти Docker VM не поместятся, а демонстрационная ценность (изоляция) уже достигается разными БД. Для боевой системы с разными вендорами
вариант 2 был бы правильным — это цена учебного упрощения.

## Цена выбора
- **Общая зона отказа**: падение кластера или потеря кворума etcd отключает все четыре сервиса сразу (Э6, Э10 журнала); у разных вендоров в жизни это не так.
- Общий лимит `max_connections = 100` на четыре базы — отсюда обязательный пул (Э7).
- Один поток WAL: логическая репликация/CDC настраивается **на базу** (slot и publication per database), `wal_level = logical` — один на кластер.
- Один релизный цикл PostgreSQL и Patroni для всех четырёх «систем разных вендоров».
