# ADR-0008. PgBouncer в режиме transaction pooling

## Контекст
`max_connections = 100` на кластер с четырьмя базами. Приложение, чекер и генератор подключаются через пул (требование базовой части). Эксперимент Э7: без пула отказы начинаются уже на 100 одновременных клиентах.

## Рассмотренные варианты
1. **Без пула** — клиенты ходят прямо в HAProxy.
2. **PgBouncer, `pool_mode = session`** — безопасно для состояния сессии (`SET`, временные таблицы, advisory-блокировки).
3. **PgBouncer, `pool_mode = transaction`**, `default_pool_size = 20`, `max_client_conn = 1000`.

## Выбор
Вариант 3: два экземпляра — запись (`:6432` → HAProxy → лидер) и чтение (`:6433` → HAProxy → реплики); пул не знает, кто лидер, это скрывает HAProxy. Параметры сессии, на которые рассчитывают клиенты (`timezone`, `datestyle`), заданы на уровне сервера в Patroni,
а не через `SET` в сессии. CDC и любой клиент, которому нужно состояние сессии, ходят **мимо пула** (`:5400`).

## Отвергнутая альтернатива и причина
**Session pooling (вариант 2)** отвергнут: он не мультиплексирует — одна клиентская сессия занимает серверное соединение, пока жива, поэтому при 900 клиентах, держащих соединения, потребовалось бы 900 серверных
(лимит — 100) либо клиенты ждали бы освобождения чужих сессий. Т.е. он ничего не даёт против исходной проблемы (наплыв клиентов), в отличие от transaction pooling: в Э7 900 клиентов обслужены 20 серверными соединениями без единой ошибки.

## Цена выбора
- **Состояние сессии не сохраняется** между транзакциями (измерено в Э7): `SET` без `LOCAL` исчезает и «протекает» к чужому клиенту, временные таблицы пропадают, сессионная advisory-блокировка не снимается и висит на серверном соединении
  (пришлось перезапускать пул). Серверные prepared statements на уровне протокола PgBouncer 1.17 не поддерживает.
- **Логическая репликация/CDC через пул невозможна** (протокол репликации) — отдельный маршрут `:5400`.
- Пул **медленнее на одиночном подключении**: +8.3 мс (13.8 против 5.5 мс медиана) — SCRAM-аутентификация и дополнительный прыжок; польза — защита `max_connections` и очередь вместо отказа.
- Пароли хранятся в `userlist.txt` открытым текстом (учебный стенд; в боевой системе — `auth_query` или хэши).
