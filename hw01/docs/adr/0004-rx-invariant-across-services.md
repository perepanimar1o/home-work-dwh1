# ADR-0004. Инвариант I10: рецептурный препарат не отпускается без рецепта

## Контекст
Признак рецептурности (`is_rx`) принадлежит **каталогу** (`catalog_service`), а ограничение «позиция с рецептурным препаратом не может попасть в документ без рецепта» нужно в **POS** (`pos_service`) — там продают.
Базы физически разные (разные вендоры по условию), кросс-сервисных `FOREIGN KEY`, `postgres_fdw`/`dblink` как «замена FK» быть не должно. Ограничение обязано быть в схеме, а не только в генераторе данных.

## Рассмотренные варианты
1. **Проверять только в приложении/генераторе** — запрещено условием («инвариант, реализованный только в генераторе, не инвариант»).
2. **Запрашивать каталог из триггера POS** через `postgres_fdw`/`dblink` в момент вставки позиции.
3. **Локальная копия справочника в POS (`pos.sku_ref`) + snapshot признака в позиции + триггеры в POS.**

## Выбор
Вариант 3. В POS живут: `pos.sku_ref(sku_bk, sku_name, is_rx, is_rx_since)` — копия нужных полей каталога, `receipt_line.is_rx_snapshot` — признак **на момент продажи** (требование snapshot-полей),
`BEFORE INSERT`-триггер позиции запрещает пометить рецептурный SKU как безрецептурный (после даты перевода в `rx`), и **отложенный** `CONSTRAINT TRIGGER`
(`DEFERRABLE INITIALLY DEFERRED`) на документе/позициях/оплатах проверяет в конце транзакции, что у документа с рецептурной позицией есть рецепт (`P0001`).
Тот же приём — `pos.batch_ref` — даёт проверку I8 (нельзя продать просроченную партию), так как срок годности живёт на складе.

## Отвергнутая альтернатива и причина
**Вызов каталога из триггера через FDW (вариант 2)** отвергнут: он превращает кросс-сервисную ссылку в синхронную runtime-зависимость — продажа в аптеке не может быть записана, пока доступен/быстр каталог другого вендора
(связывание доступности двух систем), каждая вставка позиции получает сетевой вызов, а по сути это тот же FOREIGN KEY между базами, который условие запрещает. Локальная копия делает запись автономной.

## Цена выбора
- **Копию нужно синхронизировать** (события каталога/CDC из ДЗ №2). В этом ДЗ её наполняет генератор в той же загрузке — это стенд для события синхронизации, а не сама синхронизация.
- **Окно рассинхронизации**: если каталог перевёл SKU в рецептурные, а `sku_ref` ещё не обновлён, POS на это окно пропустит продажу без рецепта (ограничение защищает от ошибок кассира, но не от запаздывания копии). Для этого есть `is_rx_since`: проверка применяется только к продажам после даты перевода.
- Дублирование данных (название, признак) и ещё одна таблица на сопровождение; `X10` (чекер) мягко допускает ≤ 5 % расхождений между snapshot и каталогом именно из-за переводов `rx → otc`.
